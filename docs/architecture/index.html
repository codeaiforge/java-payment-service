Trace
  1. Client sends POST /payments with a Bearer JWT and an Idempotency-Key.
  2. Spring Security validates the token; the rate limiter takes a token from the customer's buckets, rows in PostgreSQL shared by every replica.
  3. CreatePaymentService checks the key: a retry with the same key gets the same payment back; a different body under the same key is refused.
  4. AccountStateValidator asks the account system (Feign, retry + circuit breaker) that the source account exists, is usable and belongs to the caller.
  5. The payment is stored CREATED with its idempotency record in one transaction; the client gets 201.
  1. POST /payments/{id}/execute: access is checked, a message goes to payment-processing, and the client gets 202 only after the broker acknowledged it.
  2. PaymentProcessingConsumer turns the message into an execute command, as the controller does for HTTP.
  3. Authorization system → AUTHORIZED; limit system → PROCESSING. Each status change is its own short transaction with its audit row, committed before the next external call.
  4. Payment system POST /payment-orders/{key}: SETTLED → COMPLETED, REJECTED → FAILED, no answer → stays PROCESSING for reconciliation. Never retried.
  5. The final status writes a payment_outbox row in the same transaction.
  6. A thrown error goes through retry topics after 5s, 10s and 20s, then to payment-processing-dlt. A duplicate message is refused by the state machine itself.
  1. Every final status change of a payment or refund inserts a payment_outbox row with the change, plus the current traceparent.
  2. PaymentEventRelay runs every second on every replica and claims each payment's oldest unpublished row with FOR UPDATE SKIP LOCKED, so order per payment holds.
  3. The event is written as Avro, its schema checked in Apicurio (FULL_TRANSITIVE), and sent to payment-events keyed by payment ID. A row is marked published only after the ack: at least once, never lost.
  4. Group payment-statement projects it into statement_line, recording the event ID in the same transaction to drop duplicates. That read model serves GET /accounts/{id}/statement.
  5. Group payment-webhooks queues a delivery for each active endpoint of the payer.
  6. Published rows are kept 7 days, then deleted hourly by one replica (ShedLock). The topic itself is kept forever, so the statement can be rebuilt by replay.
  1. Every minute, one replica takes the reconciliation ShedLock row, timed by the database clock.
  2. It finds payments and refunds that have been PROCESSING for more than 2 minutes, longer than the payment system's 6s deadline.
  3. It asks the payment system GET /payment-orders/{key} or /refund-orders/{key}.
  4. A clear answer is stored by compare-and-set with its audit row and outbox event; still no answer waits for the next run.
  5. PaymentsStuckInProcessing fires when the oldest is over 120s, and is held back while the payment system's breaker is open.
  1. A customer registers an HTTPS endpoint with POST /webhooks; addresses inside our network are refused.
  2. WebhookDeliveryConsumer turns each payment event into one webhook_delivery per active endpoint of the customer holding the source account.
  3. Every second, each replica claims due deliveries by lease, with no transaction held open during the send.
  4. HttpWebhookSender posts signed JSON (v1=HMAC-SHA256 over id.timestamp.body) through the SSRF-checking resolver, with no redirects and a 15s deadline.
  5. 2xx is delivered; anything else backs off exponentially with jitter. Past the maximum age it is FAILED and counted against the endpoint, which may be disabled.
  1. Prometheus scrapes /actuator/prometheus every 5s, with exemplars carrying trace IDs.
  2. Spans go to Tempo over OTLP/HTTP. The traceparent travels in HTTP and Kafka headers and in the outbox row, so one trace runs from the request to the consumer's calls.
  3. Every log line goes to the console as ECS JSON and to Loki over OTLP, with trace_id, span_id and correlationId.
  4. Multi-window burn-rate alerts on two SLOs (99.5% execution success; 99% of POST /payments within 500ms), plus outbox lag, open breakers, stuck payments and a log-based alert.
  5. Alertmanager sends page or ticket and holds back alerts another one explains. Each alert has a runbook in docs/runbooks.

Marked shortcuts in the code that the diagram reflects: one rate-limit tier for every customer; the relay auto-registers its schema; an open breaker on execution is reported as UNKNOWN; payment-events grows without a snapshot. Every topic has one partition, so each consumer group is served by one pod whatever the replica count; the HPA scales on CPU for the HTTP side.
